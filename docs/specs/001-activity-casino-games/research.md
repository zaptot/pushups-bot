# Research: Казино-игры в Discord Activity

## 1. Где живёт серверная часть

- **Decision**: HTTP API внутри того же Go-процесса, что и бот (`net/http` стандартной библиотеки, маршруты вида `POST /api/roulette` из Go 1.22+). Сервер стартует, только если задан `ACTIVITY_PORT`.
- **Rationale**: Напрямую переиспользуются `db`, транзакции, `userStats`, и сессия бота для проверки участника. Ноль новых Go-зависимостей. Существующий деплой не меняется, пока переменная не задана.
- **Alternatives considered**: Отдельный сервис (дублирование доступа к базе и правил); Node-бэкенд из примеров Discord (второй язык на сервере).

## 2. Фронтенд

- **Decision**: Vite + TypeScript без UI-фреймворка, игры рисуются на `<canvas>` 2D. Зависимости: `@discord/embedded-app-sdk`, `vite`, `typescript`.
- **Rationale**: Четыре экрана с canvas-анимацией и парой кнопок; фреймворк не нужен. Минимум зависимостей и размер бандла.
- **Alternatives considered**: React (лишний слой для canvas-игр), PixiJS/Phaser (тяжело для 2D-колеса, шарика и карт), Matter.js для Plinko (физика не обязана совпасть с решением сервера, см. п. 8).

## 3. Вход: Discord и режим разработки

- **Decision**: `POST /api/session`. В Discord: фронтенд получает `code` через `discordSdk.commands.authorize({ scope: ['identify'] })`, сервер меняет его на `access_token` (`POST https://discord.com/api/oauth2/token`), получает пользователя (`GET /users/@me`), проверяет членство в сервере через бота (`GET /guilds/{guild}/members/{user}`) и выдаёт свой случайный токен сессии (32 байта, в памяти, 24 часа). В режиме разработки (`ACTIVITY_DEV_USER_ID` задан) `code` не нужен: сессия выдаётся этому пользователю на сервере `GUILD_ID`.
- **Rationale**: `guildId` приходит с клиента и не доверенный, поэтому членство проверяет бот. ID приложения совпадает с ID бота, отдельный `DISCORD_CLIENT_ID` не нужен; фронтенд берёт его из `GET /api/config`. Сессии в памяти: после перезапуска фронтенд просто входит заново.
- **Alternatives considered**: Подписанные HMAC-токены (stateless, но больше кода без выгоды для одного процесса); проверка `access_token` Discord на каждый запрос (лишние запросы и лимиты).
- **Proxy**: внутри Discord запросы идут через `/.proxy/api/...`, вне Discord — `/api/...`. Признак Discord — параметр `frame_id` в URL.

## 4. Запись результата и защита от повторов (FR-003, FR-006, FR-015)

- **Decision**: Новая таблица `casino_bets` (id ставки — первичный ключ, итог и данные для повторного показа в JSONB). Итог пишется строкой в `casino_bets`; учёт отжиманий (`entries`) не трогается, ставки идут в фантиках. Для игр за один ход id генерирует клиент (`crypto.randomUUID()`); повтор с тем же id возвращает сохранённый результат. Для блэкджека и рокетки id — серверный id партии/раунда.
- **Rationale**: Фантики не связаны с отжиманиями, поэтому статистика бота не меняется. Уникальный ключ исключает двойную ставку даже после перезапуска.
- **Alternatives considered**: Кэш повторов в памяти (после перезапуска повтор запишет вторую ставку); кошелёк фантиков — отложен до новой экономики.

## 5. Округление дробных выплат

- **Decision**: Случайное округление: `floor(x) + (rand < frac(x) ? 1 : 0)`. Спецификация обновлена (FR-003).
- **Rationale**: Округление вниз на ставке 10 отнимает в среднем ~0,5 фантика (~5%), что в разы больше заявленного 1%. Случайное округление сохраняет среднее точно и не сложнее по коду.
- **Alternatives considered**: Вниз (скрытая доля казино до 5%); к ближайшему (смещение около половинок).

## 6. Рулетка

- **Decision**: Европейская, 0–36, красные: 1, 3, 5, 7, 9, 12, 14, 16, 18, 19, 21, 23, 25, 27, 30, 32, 34, 36. Выплаты (возврат с учётом ставки): цвет / чёт-нечет / 1–18 / 19–36 — x2, дюжина — x3, число — x36. Ноль проигрывает во всех ставках, кроме ставки на число 0.
- **Rationale**: Стандарт, ожидание 36/37 ≈ 97,3% для всех типов.

## 7. Plinko: таблицы множителей

- **Decision**: 27 таблиц не хранятся, а вычисляются при старте: `m_k = c · g^|k − n/2|`, где `g` = 1.45 / 1.9 / 2.6 для низкого / среднего / высокого риска, а `c` подобран так, чтобы `Σ C(n,k)/2^n · m_k = 0.99`. Множители округляются до сотых к ближайшему.
- **Rationale**: Одна формула вместо 27 ручных таблиц; возврат проверяется тестом точно, по биномиальным вероятностям. Прототип: 8 рядов низкий риск — края x2.74, центр x0.62; 16 рядов высокий риск — края x184, центр x0.08.
- **Alternatives considered**: Скопированные таблицы известных казино (27 чисел-констант без гарантии 99%, риск опечатки).

## 8. Plinko: анимация

- **Decision**: Сервер генерирует путь — `n` случайных бит (0 влево, 1 вправо); лунка = число единиц. Клиент анимирует шарик по этим точкам с параболами между штырьками.
- **Rationale**: Экран гарантированно совпадает с начислением (acceptance-сценарий 2).

## 9. Блэкджек

- **Decision**: Одна колода из 52 карт, тасуется на каждую партию; дилер добирает до 17 и стоит на любых 17; блэкджек x2.5, победа x2, ничья x1. Если у дилера открыт туз или десятка, блэкджек дилера проверяется сразу. «Удвоить» — только на первых двух картах, ставка ×2 и ровно одна карта. Состояние — в памяти (`map[guild+user]*hand`), одна активная партия на игрока. Таймер `time.AfterFunc(2m)` делает «Хватит». Каждое действие несёт номер шага `seq`; несовпадающий `seq` не меняет партию и возвращает текущее состояние (повторы безопасны).
- **Rationale**: Спецификация допускает потерю незавершённой партии при перезапуске; ставка пишется только в конце, поэтому двойного начисления нет.
- **Alternatives considered**: Партии в Postgres (выживают перезапуск, но лишний код и запросы на каждый ход); 6 колод (без разницы при перетасовке каждую партию).

## 10. Рокетка (своя у каждого игрока)

- **Decision**: Точка взрыва при старте: `crash = max(1.00, floor(99 / (1 − U)) / 100)`, ограничение x100; рост `m(t) = e^{0.06·t}` (x2 за ~11,6 с, x100 за ~77 с). Вывод: сервер считает `m` по своим часам с момента старта; если `m ≥ crash`, ставка проиграна. Автовывод (от x1.01 до x99.99) срабатывает, если `auto < crash`. Конец раунда клиент узнаёт долгим опросом `GET /api/rocket/{id}` (до 25 с на запрос), поэтому точку взрыва он не знает заранее. Одна активная ракета на игрока.
- **Rationale**: `P(crash ≥ m) ≈ 0.99/m`, то есть возврат 99% при любой стратегии. Для игры в одиночку WebSocket не нужен: долгий опрос — это обычные HTTP-запросы через прокси Discord.
- **Alternatives considered**: WebSocket (нужен только для общего раунда, который не выбран); выдать клиенту точку взрыва (тогда можно жульничать).

## 11. Раздача фронтенда

- **Decision**: При разработке страницы раздаёт Vite (`npm run dev`) и проксирует `/api` в Go. Для публикации Go раздаёт собранную папку из `ACTIVITY_DIR` (по умолчанию `activity/dist`) через `http.FileServer`.
- **Rationale**: Без `go:embed` сборка Go не зависит от наличия `dist`. Вопрос хостинга отложен (спецификация, Assumptions).

## 12. Проверки

- **Decision**: Один файл `casino_test.go`: чистые тесты математики без базы (возврат рулетки и Plinko точно, рокетки — моделированием 200 000 раундов, правила блэкджека на заданных колодах, случайное округление) и один интеграционный тест на настоящей базе в откатываемой транзакции (как в `bot_test.go`): ставка через HTTP-обработчик в режиме разработки, повтор с тем же id даёт одну запись.
